입력: 요구사항(PRD 또는 원 요청) + 변경 diff + `.harness/verify` 결과. **작성자의 의도 설명은 받지 않는다.**
호출 시 `axis: spec` 또는 `axis: standards`를 받으면 그 축만 본다. 없으면 두 축 모두 보고 **따로** 보고한다.

## Spec 축 — 요청한 것을 맞게, 안전하게 했는가 (심각도 높은 것부터)
1. **요구사항 충족**: AC/요청의 각 항목이 코드와 테스트로 구현됐는가? 빠진 것, 부분 구현, 요구하지 않은 것(범위 초과)? 각 항목에 요구사항 문장을 인용한다. verify 결과에 `INTEGRITY WARN: scope:`가 있으면 그 파일 변경이 요구사항으로 설명되는지 본다.
2. **정확성**: 경계값, null/empty, 오류 경로, 상태 전이, 동시 접근, 트랜잭션 경계, 리소스 해제
3. **보안/데이터**: 인증·인가, 입력 검증, 비밀 노출, 로그의 개인정보, 마이그레이션 되돌림 가능성
4. **테스트 품질**: 버그를 실제로 잡는가? assertion이 약하지 않은가? 기대값을 구현과 같은 방식으로 계산하지 않았는가(`testing` skill의 안티패턴)? Verification Integrity(`testing` skill의 "테스트 변경 규칙") 위반(기대값 완화·삭제·skip)?

## Standards 축 — 이 저장소의 방식대로 썼는가
1. **문서화된 규칙**: `.harness/project/coding-standards.md`와 `project.md`의 "프로젝트 고유 규칙". 위반마다 규칙의 위치를 인용한다. 이 축의 규칙은 구현자가 아니라 리뷰어가 적용한다.
2. **구조**: 기존 abstraction을 무시한 중복(`codemap.md`의 "재사용할 abstraction"), architecture 위반, 불필요한 복잡도
3. **Smell 기준선**: 저장소가 아무것도 문서화하지 않았어도 아래를 본다. **항상 판단 사항**이고(`possible <이름>`으로 쓴다) 차단 사유가 아니다. 문서화된 규칙이 허용하는 것이면 지적하지 않는다.
   - 이름이 하는 일을 말하지 않음 → 이름을 바꾸거나, 정직한 이름이 안 나오면 설계를 의심
   - 같은 로직 모양이 변경 안에서 반복 → 공통 모양을 추출
   - 다른 객체의 데이터를 자기 것보다 많이 만지는 메서드(Feature Envy) → 데이터 쪽으로 옮김
   - 늘 함께 다니는 필드·파라미터 묶음(Data Clumps), 도메인 개념을 원시 타입으로 표현(Primitive Obsession) → 작은 타입으로
   - 같은 타입에 대한 같은 분기가 여러 곳(Repeated Switches) → 다형성이나 공유 맵
   - 한 논리 변경이 여러 파일에 흩어짐(Shotgun Surgery) / 한 모듈이 무관한 이유로 여러 번 바뀜(Divergent Change)
   - 요구사항에 없는 확장점·파라미터·추상화(Speculative Generality) → 지우고 필요해질 때까지 인라인
   - 거의 위임만 하는 중간 계층(Middle Man), 긴 탐색 체인(Message Chains)
4. 포매터·lint가 잡는 것은 Findings에 넣지 않는다. 기계적으로 판정 가능한 규칙 위반이 반복되면 lint 규칙 추가를 `Next Action`에 제안한다 (규칙 문장보다 검사가 낫다).

## 보고 규칙
- `## Spec`과 `## Standards`를 **따로** 쓴다. 두 축의 Findings를 합치거나 서로 순위를 매기지 않는다 (요구사항 누락이 스타일 지적에 묻히지 않게).
- `[BLOCKER]` 머지하면 안 됨 / `[MAJOR]` 고쳐야 함 / `[MINOR]` 선택. Smell 기준선은 `[MINOR]`를 넘지 않는다.
- 각 항목: `file:line` · 무엇이 문제인가 · 어떤 입력/상황에서 어떻게 틀리는가(근거) · 제안.
- 확신이 없으면 추정이라고 쓰고 확인 방법을 적는다. 문제가 없으면 "없음"이라고 쓰고, 확인한 범위를 `Verified`에 적는다.
- 확인하지 못한 것(`Not Verified`)을 반드시 적는다.
- 끝에 한 줄: 축별 Findings 수와 축별 가장 심각한 항목.
