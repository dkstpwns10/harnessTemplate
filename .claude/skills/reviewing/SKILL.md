---
name: reviewing
description: 변경 사항을 리뷰하는 순서와 보고 규칙 (요구사항 충족, 정확성, 보안, 테스트 품질). 코드 리뷰를 수행할 때 사용.
---



입력: 요구사항(PRD 또는 원 요청) + 변경 diff + `.harness/verify` 결과. **작성자의 의도 설명은 받지 않는다.**

## 확인 순서 (심각도 높은 것부터)
1. **요구사항 충족**: AC/요청의 각 항목이 코드와 테스트로 구현됐는가? 빠진 것, 요구하지 않은 것(범위 초과)?
2. **정확성**: 경계값, null/empty, 오류 경로, 상태 전이, 동시 접근, 트랜잭션 경계, 리소스 해제
3. **보안/데이터**: 인증·인가, 입력 검증, 비밀 노출, 로그의 개인정보, 마이그레이션 되돌림 가능성
4. **테스트 품질**: 버그를 실제로 잡는가? assertion이 약하지 않은가? Verification Integrity(`testing` skill의 "테스트 변경 규칙") 위반(기대값 완화·삭제·skip)?
5. **구조**: 기존 abstraction 무시한 중복, architecture 위반, 불필요한 복잡도
6. 스타일 취향은 Findings에 넣지 않는다 (lint가 잡을 것).

## 보고 규칙
- `[BLOCKER]` 머지하면 안 됨 / `[MAJOR]` 고쳐야 함 / `[MINOR]` 선택.
- 각 항목: `file:line` · 무엇이 문제인가 · 어떤 입력/상황에서 어떻게 틀리는가(근거) · 제안.
- 확신이 없으면 추정이라고 쓰고 확인 방법을 적는다. 문제가 없으면 "없음"이라고 쓰고, 확인한 범위를 `Verified`에 적는다.
- 확인하지 못한 것(`Not Verified`)을 반드시 적는다.
