일반 문법·패턴 설명은 하지 않는다. 이 프로젝트에서 지킬 것만.

## 변경 전
- `.harness/project/codemap.md`의 "재사용할 abstraction"과 "확인된 함정"을 먼저 본다.
- 같은 일을 하는 기존 코드/유틸/패턴을 먼저 찾는다 (Grep). 있으면 재사용하거나 확장한다. 새 abstraction은 기존 것이 명백히 맞지 않을 때만.
- 주변 코드의 이름 규칙, 에러 처리, 로깅, 패키지 구조를 따른다. 한 파일 안에서 스타일을 섞지 않는다.

## 변경 중
- 요청 범위만 수정. 포맷 정리·이름 변경·"겸사겸사" 개선 금지 (필요하면 제안으로 남긴다).
- 에러를 삼키지 않는다. 의도된 무시는 이유를 주석으로.
- 주석은 "왜"만. 코드가 말하는 "무엇"은 쓰지 않는다.
- 비밀 값, 환경 의존 경로를 코드/테스트에 하드코딩하지 않는다.
- 공개 API·DB 스키마·이벤트 형식 변경은 FULL 위험 신호다 — 멈추고 Triage를 다시 한다.

## 변경 후
- `.harness/verify quick` → 통과 확인. 변경한 동작에 대응하는 테스트가 있는지 확인.
- 디버깅용 임시 코드/로그가 남지 않았는지 `git diff`로 점검.

## 프로젝트 고유 규칙
`.harness/project/project.md`의 "프로젝트 고유 규칙"을 따른다.
